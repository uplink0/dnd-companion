# Game State Architecture

## Главный принцип

**Персонаж — центральный субъект состояния игры.**

Все игровые действия исходят от персонажа или происходят с персонажем. Эти действия изменяют единое состояние кампании. Остальные разделы приложения не являются независимыми источниками состояния — они показывают производные данные из состояния игры.

```text
ПЕРСОНАЖ
   |
   | действие / событие
   v
GAME ENGINE
   |
   | проверка правил
   v
ИЗМЕНЕНИЕ СОСТОЯНИЯ
   |
   v
GAME EVENT
   |
   +----> CHARACTER STATE
   +----> INVENTORY
   +----> BESTIARY / KNOWLEDGE
   +----> MAP / LOCATIONS
   +----> JOURNAL
   +----> QUESTS
   +----> CHAT / MASTER HISTORY
```

## Источник истины

Страницы не должны напрямую менять состояние друг друга.

Нельзя строить архитектуру вида:

```text
chat.js -> inventory.js
chat.js -> map.js
chat.js -> journal.js
```

Правильная схема:

```text
PLAYER ACTION
    -> GAME ENGINE
    -> STATE CHANGE
    -> GAME EVENT
    -> READ MODELS / API
    -> UI pages
```

UI только отправляет команду и затем получает актуальное состояние через API.

## Что считается действием

Примеры игровых команд:

- USE_ITEM
- RECEIVE_ITEM
- DROP_ITEM
- EQUIP_ITEM
- UNEQUIP_ITEM
- MOVE_CHARACTER
- DISCOVER_LOCATION
- SEARCH_LOCATION
- ENCOUNTER_CREATURE
- STUDY_CREATURE
- DEFEAT_CREATURE
- ACCEPT_QUEST
- COMPLETE_QUEST
- TAKE_DAMAGE
- HEAL_CHARACTER
- APPLY_EFFECT
- REMOVE_EFFECT
- PLAYER_MESSAGE
- MASTER_RESPONSE

Каждая команда должна проходить через игровой движок, который проверяет персонажа, кампанию, доступность объекта и правила действия.

## Инвентарь

Инвентарь является состоянием персонажа.

Примеры:

```text
USE_ITEM
  -> inventory.quantity -= 1
  -> применить эффект предмета
  -> записать GAME_EVENT ITEM_USED
  -> журнал/история получают событие
```

```text
RECEIVE_ITEM
  -> создать или увеличить inventory entry
  -> записать GAME_EVENT ITEM_RECEIVED
  -> предмет автоматически появляется на странице предметов
```

Страница предметов не должна сама решать, когда уменьшать или добавлять предмет.

## Бестиарий

Бестиарий должен быть персональным знанием персонажа.

Сам факт существования существа в БД мира не означает, что существо известно персонажу.

Пример:

```text
WORLD CREATURE: Goblin
        |
        | персонаж встретил
        v
CREATURE_ENCOUNTERED
        |
        v
CHARACTER KNOWLEDGE
        |
        +-> бестиарий персонажа
```

Пока персонаж никого не встретил/не изучил/не победил, его бестиарий должен оставаться пустым.

Другой персонаж может знать другое количество существ в той же кампании.

## Карта

Карта также должна учитывать знание и продвижение конкретного персонажа.

Разделяем:

- существует в мире;
- известно персонажу;
- открыто персонажем;
- посещено персонажем;
- исследовано персонажем.

Например:

```text
MOVE_CHARACTER
    -> current_location меняется
    -> LOCATION_VISITED
    -> локация становится посещённой персонажем
    -> карта и журнал показывают новый результат
```

## Журнал

Журнал — это история жизни персонажа, формируемая из игровых событий.

Он не должен быть отдельным несвязанным хранилищем, которое приходится вручную синхронизировать с чатом, инвентарём или картой.

Пример последовательности:

```text
вошёл в руины
-> LOCATION_VISITED

нашёл зелье
-> ITEM_RECEIVED

увидел гоблина
-> CREATURE_ENCOUNTERED

изучил гоблина
-> CREATURE_STUDIED

победил гоблина
-> CREATURE_DEFEATED
```

Журнал отображает эту цепочку в понятном пользователю виде.

## Чат Мастера

Чат — это интерфейс действий и повествования, а не отдельная игровая система.

Сообщение персонажа может привести к игровым последствиям.

Например:

```text
Игрок: выпиваю зелье
        |
        v
GAME ENGINE
        |
        +-> USE_ITEM
        +-> inventory -1
        +-> effect applied
        +-> GAME_EVENT
        +-> journal
```

Ответ Мастера также должен быть связан с событием/результатом игрового действия, а не существовать отдельно от состояния мира.

## Общий API-контракт

Для активного персонажа API должно позволять получить согласованное состояние:

```text
active character
character stats
inventory
active effects
known creatures
known/discovered locations
quests
journal/events
chat history
```

Все эти данные должны быть согласованы по `campaign_id` и `character_id`.

Нельзя допускать, чтобы API вернул персонажа одной кампании, а его инвентарь или историю другой кампании.

## Game Events

`game_events` является центральным журналом изменений состояния.

Рекомендуемые типы:

```text
CHARACTER_CREATED
CHARACTER_MOVED
LOCATION_DISCOVERED
LOCATION_VISITED
ITEM_RECEIVED
ITEM_FOUND
ITEM_USED
ITEM_DROPPED
ITEM_EQUIPPED
ITEM_IDENTIFIED
CREATURE_ENCOUNTERED
CREATURE_STUDIED
CREATURE_DEFEATED
QUEST_ACCEPTED
QUEST_PROGRESS
QUEST_COMPLETED
DAMAGE_TAKEN
HEALING_RECEIVED
EFFECT_APPLIED
EFFECT_REMOVED
PLAYER_ACTION
MASTER_RESPONSE
```

Событие должно содержать минимум:

```text
campaign_id
actor_character_id
actor/aggregate type
aggregate_id
payload
created_at
```

## Правило разработки новых механик

Перед реализацией любой новой механики нужно ответить на четыре вопроса:

1. Какое действие выполняет персонаж?
2. Какое состояние игры меняется?
3. Какое событие фиксирует это изменение?
4. Какие страницы должны увидеть новое состояние через API?

Если механика требует прямого вызова одного UI-раздела из другого UI-раздела, архитектуру нужно пересмотреть.

## Главное требование

**От персонажа должны идти ниточки во всё остальное через игровой движок и единое состояние игры.**

Создание персонажа только создаёт начальное состояние. Далее вся жизнь персонажа должна формировать и изменять мир: предметы, эффекты, встречи, бестиарий, карту, квесты, журнал и историю чата.

Карточка созданного персонажа и существующий UI не должны без необходимости менять свой внешний вид из-за внутренних архитектурных изменений.
